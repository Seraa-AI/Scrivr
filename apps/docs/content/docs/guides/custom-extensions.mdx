description: Building an extension for a Canvas-based editor without DOM rendering.

Building a custom extension for Scrivr is fundamentally different from building one for a DOM-based toolkit like TipTap or Slate. Because Scrivr bypasses the DOM entirely, you cannot simply return a React component or an HTML string string. 

You must define the strict mathematical layout and explicitly tell the engine how to paint your elements on the Canvas context.

---

## 3 Core Components of a Custom Extension

When building a new Node or Mark (e.g., an Image block, a Custom Highlight, a Kanban Board), you must complete three steps:

1. **The Schema (Model Layer)**
   Register the Node or Mark within the ProseMirror schema. This tells the document tree what attributes, structure, and HTML parse/serialize rules are allowed.
2. **The Measurer (Layout Layer)**
   Write a dimension resolver that hooks into `BlockLayout.ts`. The layout engine needs to calculate exactly how wide and how tall your element is (in world-space pixels) so it can position siblings and paginate correctly.
3. **The Painter (Rendering Layer)**
   Register a draw handler with `PageRenderer.ts` that issues native HTML5 Canvas drawing commands (`ctx.fillRect`, `ctx.drawImage`) corresponding to the bounding box calculated in Step 2.

---

## A Simple Custom Highlight (Mark)

Let's build a simple inline highlighter that draws a background color over text.

### Step 1: Schema Definition

```typescript title="HighlightMark.ts"
import { Mark, mergeAttributes } from "@tiptap/core";
// Under the hood, we extend TipTap's architecture for schema management

export const HighlightMark = Mark.create({
  name: "highlight",

  addAttributes() {
    return {
      color: {
        default: "#ffff00", 
      },
    };
  },

  renderHTML({ HTMLAttributes }) {
    return ["mark", mergeAttributes(HTMLAttributes), 0];
  },
});
```

### Step 2: The Layout Measurer

For inline marks, the width and height are handled inherently by `TextMeasurer` based on the text string. 

However, for block-level nodes (like an `<Image>`), you must define the dimensions explicitly. In a fully custom block:

```typescript title="ImageNode.ts"
// Example pseudo-code for a Block node
export const ImageNode = Node.create({
  name: "image",
  // ... schema

  addNodeView() {
    // You must provide bounds logic.
    return {
      measure(node) {
        // Return physical world-space pixels
        return {
          width: node.attrs.width || 400,
          height: node.attrs.height || 300,
        };
      }
    }
  }
});
```

### Step 3: The Canvas Painter

The hardest part: drawing the highlight.

When the `PageRenderer` traverses the `DocumentLayout`, it triggers rendering hooks based on Mark/Node names.

```ts title="Renderer.ts"
// In your application or extension registry:
import type { PageRenderer } from "@scrivr/core";

export function registerHighlightPainter(editor) {
  editor.registerPainter("mark:highlight", (ctx: CanvasRenderingContext2D, args) => {
    // args contains the world-space bounding box calculated by BlockLayout
    const { x, y, width, height, node } = args;

    // The current color specified in the ProseMirror attributes
    const color = node.attrs.color;

    ctx.save();
    
    // Draw the background rectangle
    ctx.fillStyle = color;
    ctx.fillRect(x, y - height, width, height);
    
    // Wait... what about the text?
    // Scrivr will draw the text run automatically AFTER marks are painted.
    
    ctx.restore();
  });
}
```

<Callout type="warn">
  Remember that Canvas drawing order matters! Backgrounds (like Highlights) must be drawn *before* the text run is explicitly drawn by the `PageRenderer`, otherwise the highlight will paint over the text and obscure it.
</Callout>

## Customising a built-in extension

When a built-in does almost what you need, `extend` makes a new extension from it without copying it. A hook you declare replaces the original's. `this.parent` calls the original's hook with the same context and arguments, so you can change its result or add to it. Any hook you leave out stays the original's.

```typescript
import { Bold, Editor, Heading, StarterKit } from "@scrivr/core";

// One more attribute on the heading node; everything else stays Heading's.
const AnchoredHeading = Heading.extend({
  addNodes() {
    const { heading, ...rest } = this.parent?.() ?? {};
    return { ...rest, heading: { ...heading, attrs: { ...heading?.attrs, anchor: { default: null } } } };
  },
});

// Keep Bold's commands and add one.
const MyBold = Bold.extend({
  addCommands() {
    return { ...this.parent?.(), toggleStrong: () => (state, dispatch) => true };
  },
});

new Editor({
  extensions: [StarterKit.configure({ heading: false, bold: false }), AnchoredHeading, MyBold],
});
```

- **Replacing a built-in that StarterKit includes:** turn it off in `StarterKit.configure` and list your extended one, as above. Otherwise both register the same node or mark, and the later one wins with a warning.
- **Replacing Paragraph:** do it in place, because order matters there. The first block type registered is the one an empty document starts with, and StarterKit lists Paragraph first:

  ```typescript
  import { Paragraph, StarterKit } from "@scrivr/core";

  const MyParagraph = Paragraph.extend({ /* your overrides */ });
  const Kit = StarterKit.extend({
    addExtensions() {
      return (this.parent?.() ?? []).map((child) => (child.name === "paragraph" ? MyParagraph : child));
    },
  });
  ```
- **Lifecycle hooks:** an `onEditorReady` or `onViewReady` override should `return this.parent?.(editor)`, or combine it with its own cleanup. Otherwise the original's cleanup never runs on `destroy()`.
- **No original hook:** `this.parent` is `undefined` when the original doesn't declare that hook. Writing `this.parent?.()` handles both cases.
- **Options:** the extended extension starts from the original's current options, so a configured extension extends as configured. `defaultOptions` merges over them, and `configure` still works afterwards. New options must keep the original's, because its hooks still read them. Don't narrow the type of an inherited option: the compiler allows it, but the inherited value isn't re-checked.
- **Name:** `name` renames the extension, which is the name `findExtension` answers to. Keys a hook writes literally, as every built-in does, stay the same. A key built from `this.name` follows the new name. To run a built-in's copy beside the original, also override the hooks whose keys would clash.
- **Chaining:** `extend` can be chained, and each layer's `parent` is the one below it.
- **Bundles:** a bundle extends the same way. `StarterKit.extend({ addExtensions() { return [...(this.parent?.() ?? []), MyExtension]; } })` adds a child to it.

## The Complexity Of Canvas

Writing extensions in Scrivr is more mathematically demanding than other editors. If you want to render a complex React component (e.g., an interactive Kanban board table) inside the document flow, Scrivr allows you to use `OverlayRenderer` to project absolute-positioned widgets over the Canvas. See the Coordinate System documentation for `getViewportRect`!
