---
title: Sealing a revision
description: Freeze a collaborative document so every client — live, late or offline — sees the same boundary, and prove what was agreed.
---

Sealing turns a document people are editing into one that no longer changes: the wording someone approved, signed or submitted. Scrivr gives you the pieces; **your server decides when to seal and enforces it**, because a seal a modified client could skip is not a seal.

What Scrivr provides:

- a **mutation gate** — a sealed editor refuses every change, from this client and from collaborators;
- a **snapshot and hash** — the exact bytes that were agreed, and the SHA-256 that proves it;
- a **revision stamp** written into the room, so every client learns of the seal on its next sync;
- functions your HocusPocus server calls from its own hooks.

What stays yours: who may seal, the record of it, locking, authentication, storage, and who signs.

---

## Sealing, on the server

Seal inside whatever your server already uses to order a seal against a save — a row lock, a queue — after the room's latest edits are in.

```ts
import { ServerEditor, StarterKit, Field } from "@scrivr/core";
import { snapshotFromYDoc, stampSeal } from "@scrivr/plugins";
import type { Document } from "@hocuspocus/server";

const { schema } = new ServerEditor({ extensions: [StarterKit, Field] });

// `document` is the room's HocusPocus Document — a Y.Doc — e.g. `server.documents.get(name)`.
async function seal(document: Document, revisionId: string, assignedRoles: string[]) {
  const result = await snapshotFromYDoc(document, schema, { assignedRoles });
  if (!result.ok) return result.refusal; // show it to whoever asked to seal

  const { content, contentHash, fields } = result.snapshot;
  await saveSealedRevision({ revisionId, content, contentHash, fields }); // yours

  stampSeal(document, { revisionId, contentHash, sealedAt: new Date().toISOString() });
  // Connections already open stop being able to write, not only new ones.
  for (const connection of document.getConnections()) connection.readOnly = true;
  return null;
}
```

A seal is refused, with a reason, while:

| Refusal | Means |
|---|---|
| `pending-tracked-changes` | Suggestions are still open — accept or reject them first |
| `unfilled-fields` | Text the author fills still shows its prompt — fill it first |
| `unassigned-roles` | A required field's role has nobody assigned |
| `unknown-roles` | You assigned a role no field carries — its field was removed |
| `unidentified-fields` | A signer field has no id or role, or shares another's id — nobody could complete it, or two values would collide |

### Your own checks

Scrivr's checks cover what it can see in the document. Add your own, such as an approved template, a signing order, or a required counter-signature, and they refuse a seal the same way. `before` checks run ahead of Scrivr's; `after` checks run only once Scrivr's have passed. The first refusal stops the seal, and each check sees the same reading of the document the snapshot is taken from:

```ts
import type { SealCheck } from "@scrivr/core";

const inSigningOrder: SealCheck = ({ fields }) => {
  const unordered = [...new Set(fields.map((f) => f.role))].filter((role) => !signingOrder.includes(role)); // yours
  return unordered.length
    ? { reason: "host", code: "signing-order", message: `No place in the signing order for ${unordered.join(", ")}.` }
    : null;
};

await snapshotFromYDoc(document, schema, {
  assignedRoles,
  checks: { before: [templateIsApproved], after: [inSigningOrder] },
});
```

A refusal you return comes back as `{ reason: "host", code, message }`, next to Scrivr's own.

The order people *sign* in is yours too: a viewer completes only the fields you list in `FieldCompletion`'s `completable`, so leave a party's fields out until it is their turn.

## Enforcing it, in your HocusPocus hooks

```ts
import { isSealed, matchesSnapshot, resetToSnapshot } from "@scrivr/plugins";

const server = new Hocuspocus({
  async onAuthenticate({ documentName, connection }) {
    // Your own auth first. The room is not loaded yet here, so ask your own
    // record: a sealed room is read-only for everyone who joins it.
    if (await latestRevisionIsSealed(documentName)) connection.readOnly = true; // yours
  },

  async onLoadDocument({ document, documentName }) {
    // A cached room can hold edits that slipped in around the seal.
    // Put it back to exactly what was sealed.
    const sealed = await latestSealedRevision(documentName); // yours
    if (sealed && !(await matchesSnapshot(document, schema, sealed.contentHash))) {
      resetToSnapshot(document, schema, sealed.content);
    }
  },

  async onStoreDocument({ document }) {
    if (isSealed(document)) return; // a sealed revision is never rewritten
    // …your usual store
  },
});
```

The stamp is in the room itself, so a client that is already connected learns of the seal on its next sync, and `seal` has already made its connection read-only — the server drops anything it sends meanwhile.

## On the client

`Collaboration` follows the stamp. The moment it sees a seal the editor seals, so nothing more is typed into an approved revision. Then it tells you whether this client holds what was sealed:

```ts
Collaboration.configure({
  url,
  name: documentId,
  onSealed: (stamp) => showSealedBanner(stamp.revisionId),
  onStaleEdits: ({ stamp, content }) => {
    // This client had work the server never received. It is not lost:
    // keep it as a fork of the sealed revision, or let it go — then reload.
    offerToKeepAsDraft({ parentRevisionId: stamp.revisionId, content });
  },
  onRevision: () => remountEditor(), // the room was unsealed into a new revision
});
```

Leave the editor's own `sealed` option off when it joins a room. The room's content reaches it as a collaborator's change, which a sealed editor refuses, so it would open empty; the stamp seals it once the content is in. `sealed: true` is for showing a stored snapshot with no room.

## Unsealing

A sealed revision is never edited in place. Unsealing starts its successor, and the room says so:

```ts
import { stampEditable } from "@scrivr/plugins";

stampEditable(document, { revisionId: newRevisionId, parentRevisionId: sealedRevisionId });
```

Clients holding the sealed revision get `onRevision` and mount a fresh editor. A client that simply opens an editable room is not told anything.

## Proving what was agreed

- `contentHash` is over the document as agreed — never over signers' values, which are not part of it.
- `verifySnapshot(content, contentHash)` checks a stored snapshot is untouched.
- `hashArtifact(pdfBytes)` hashes the executed PDF — what was displayed, with the signatures in it.

Signing a sealed revision — fields, values, reading evidence — is in [Fields](/docs/guides/fields).
