title: Typography & Fonts
description: Give the editor an inventory of typefaces it owns, so canvas measurement and PDF export agree on what the document is set in.
---

Scrivr paints text onto a `<canvas>`, so layout depends on font metrics rather than on the browser laying text out for you. A family name like `Inter` is a **request**: what it resolves to depends on what the machine happens to have installed. That makes it useless on its own — an exporter cannot embed a request, and two machines can disagree about what the document looks like.

So the editor is given an inventory of faces it owns the bytes for. Every lane works from that one answer.

<Callout type="info">
	Scrivr never bundles a typeface. Fonts are licensed, large, and your
	choice — the engine is what resolves and records them.
</Callout>

---

## Supplying a provider

A `DefaultFontProvider` needs a default face and, usually, the other weights and slants of it. Each face is a descriptor: registering it costs nothing until something resolves to it, and only then are its bytes fetched.

```ts title="fonts.ts"
import { DefaultFontProvider, type FontResource } from "@scrivr/react";
import regular from "inter-ui/web/Inter-Regular.woff2?url";
import bold from "inter-ui/web/Inter-Bold.woff2?url";
import italic from "inter-ui/web/Inter-Italic.woff2?url";

const face = (
	id: string,
	url: string,
	weight: number,
	style: "normal" | "italic",
): FontResource => ({
	id,
	family: "Inter",
	weight,
	style,
	format: "woff2",
	// Inter is OFL-licensed, so it may travel inside an exported PDF.
	embedding: { allowed: true, source: "caller" },
	bytes: async () => (await fetch(url)).arrayBuffer(),
});

export const fonts = new DefaultFontProvider({
	default: face("inter-400", regular, 400, "normal"),
	resources: [
		face("inter-700", bold, 700, "normal"),
		face("inter-400-italic", italic, 400, "italic"),
	],
});
```

```tsx title="Editor.tsx"
const editor = useScrivrEditor({ extensions: [StarterKit], fonts });
```

That is the whole setup. The editor installs the bytes in its measurement backend under a private alias, so `measureText` reads *your* face rather than whatever the operating system maps `Inter` to.

<Callout type="info">
	Register every weight and slant you care about. A request for bold resolves
	to the nearest face in the family — with no bold registered, bold text is
	drawn in the regular weight rather than synthesised.
</Callout>

### Pick a file that covers the scripts you accept

Most font packages publish one file per script, selected in CSS by
`unicode-range`. That arrangement assumes the browser picks a file per
*character*, which it cannot do here: a face is one set of bytes, and those
same bytes have to serve measurement and embedding alike.

A Latin-only file holds around 230 glyphs. Paste Cyrillic or Greek into a
document using it and those characters have no glyph — on canvas the browser
quietly substitutes something else, and in a PDF they are drawn as blanks.

So prefer an unsubsetted file per face. `inter-ui` publishes Inter that way:
~110 KB per face, about 2 850 glyphs, covering Latin, Latin Extended, Greek,
Cyrillic and Vietnamese in one file. The faces are fetched only when something
resolves to them, so the catalogue costs nothing until it is used.

## What happens to a font you do not own

A document can name anything. A `.docx` written in Word may ask for Aptos, Calibri or Cambria, and an application that registered Inter owns none of them.

Resolution prefers, in order: the exact face asked for, another weight or slant of the same family, then the nearest face in your default's family. It never invents a family name, and it reports which of those happened:

```ts
const shortfalls = await prepareDocumentFonts(doc, fonts, {
	portable: true,
	embeddable: true,
});
// [{ request: { family: "Aptos", weight: 700 }, resolved: "Inter", source: "default" }]
```

DOCX import runs this for you and raises a `font-substituted` diagnostic per face, so you can tell the user their contract is no longer set in Aptos rather than letting them discover it.

## Exporting

`exportToPdf` resolves the document's faces under `{ portable: true, embeddable: true }` **before** any geometry is measured, embeds them, and lays the document out against the embedded faces' own metrics. The PDF is therefore set in the face it was measured in — not in a base-14 lookalike chosen from the family name.

```ts
await exportToPdf(editor, {
	onFontShortfall: (faces) => {
		for (const f of faces) {
			console.warn(`${f.request.family} exported as ${f.resolved}`);
		}
	},
});
```

Two constraints shape that answer:

| Constraint | Meaning |
| --- | --- |
| `portable` | The face must be usable off this machine. A `systemCandidates` family — one the browser can draw but nobody owns bytes for — is refused. |
| `embeddable` | The face's licence must permit it to travel inside the file. Set `embedding: { allowed: false }` on a resource that may not. |

A face that resolves but cannot be embedded fails the export rather than silently falling back, because falling back would invalidate the geometry already measured.

## Fonts that arrive late

You do **not** need to delay mounting the editor until fonts load. The editor lays out immediately with what it has, prepares the faces in the background, and when an answer changes it drops its measurement cache and reflows. Text may reflow once shortly after mount; it will not be silently mismeasured.

If your application swaps the inventory at runtime, a provider can notify the editor:

```ts
provider.subscribe((change) => {
	// "resource-added" | "resource-loaded" | "resource-failed" | "resource-removed"
});
```

The editor subscribes on your behalf; implementing `subscribe` on a custom `FontProvider` is what lets a late arrival trigger a reflow.

## Custom providers

`FontProvider` is a small interface, so an inventory backed by a font server or a user's uploaded files is a matter of implementing three methods:

```ts
interface FontProvider {
	defaultRequest(): FontRequest;
	prepare(requests, constraints?): Promise<void>; // may fetch; runs before layout
	resolve(request, constraints?): FontResolution; // never blocks; layout is sync
	subscribe?(listener): () => void;
}
```

`resolve` is synchronous because measurement cannot wait. `prepare` is where acquisition happens, and it is always called before the geometry that depends on it.
