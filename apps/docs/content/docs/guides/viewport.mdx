---
title: Viewport & Pagination
description: Configuring page dimensions, the virtual scroll window, and programmatic scrolling.
---

Scrivr renders the document as a sequence of fixed-size pages inside a scrollable container.
The `<Scrivr />` component mounts a `TileManager`, which paints only the pages near the
visible area: it keeps a small pool of page tiles and moves them as you scroll, so the number
of canvases follows the view, not the length of the document.

---

## How pages are displayed

A shown page is a `<div>` sized to `pageConfig.pageWidth × pageConfig.pageHeight` (times the
zoom), placed in a column as tall as every page and the `gap` between them. On each scroll
the tiles over the visible pages, plus `overscan` pages either side, are painted; the rest
of the column is empty space.

```
┌───── scroll container ──────┐
│  ┌── page-wrapper (div) ──┐ │
│  │  <canvas> content      │ │  ← PageRenderer
│  │  <canvas> overlay      │ │  ← OverlayRenderer
│  └────────────────────────┘ │
│     ← gap (24 default) →    │
│  ┌── page-wrapper (div) ──┐ │
│  │  <canvas> content      │ │
│  │  <canvas> overlay      │ │
│  └────────────────────────┘ │
└─────────────────────────────┘
```

## Controlling page size

Page dimensions and margins are set once via `pageConfig` in `EditorOptions`:

```ts
const editor = useScrivrEditor({
  extensions: [StarterKit],
  pageConfig: {
    pageWidth: 816, // US Letter at 96 dpi
    pageHeight: 1056,
    margins: { top: 96, right: 96, bottom: 96, left: 96 }, // 1 inch
  },
});
```

`pageConfig` is read-only after construction. See [`PageConfig`](/api/types#pageconfig) for all
fields and defaults.

---

## Gap between pages

Control the visual gap between pages with the `gap` prop on `<Scrivr />`:

```tsx
<Scrivr editor={editor} gap={40} />  {/* 40 page units between pages */}
```

Default is `24`, in page units like the page itself, so it scales with the zoom. The gap is
purely visual — it does not affect layout or pagination.

---

## Zoom

Zoom shows the document larger or smaller without changing it: lines break in the same
places at every zoom, as in Word, because layout is in page units and zoom only scales
the view. Each page is painted at the zoom's resolution, so text stays sharp at 400%.

```tsx
const editor = useScrivrEditor({ extensions: [StarterKit], zoom: "fit-width" });

editor.setZoom(1.5);         // 150% — any factor from MIN_ZOOM (0.1) to MAX_ZOOM (5)
editor.setZoom("fit-width"); // the page's width fills the view
editor.setZoom("fit-page");  // the whole page fits the view
editor.zoom;                 // the factor in effect, e.g. 0.47 for a fit on a phone
editor.zoomRequest;          // what was asked: "fit-width"
```

A fit follows the scroll container as it resizes — a phone fits the width, and rotating
it fits again — while a factor stays fixed. The default is `1`.

When the zoom changes, the line at the top of the view stays at the top. Ctrl/Cmd + scroll
and a trackpad pinch zoom about the pointer instead of zooming the whole page; turn that
off with `<Scrivr zoomGestures={false} />`. Cmd/Ctrl + `=` / `−` / `0` stay the browser's.

The page column sizes itself at the zoom, so let `<Scrivr />` take its width from its content
rather than setting one: the column then grows in the same step that keeps your place.

In React, `useZoom(editor)` gives the factor in effect and `useZoomRequest(editor)` what was
asked for — a fit, or a factor — each re-rendering as it changes. A zoom control shows the
request as chosen: picking Fit width when it equals the factor already shown changes no
factor, but the fit now follows the view.

```tsx
const zoom = useZoom(editor);
const request = useZoomRequest(editor);
return <span>{request === "fit-width" ? "Fit width" : `${Math.round(zoom * 100)}%`}</span>;
```

Everything positioned with `getViewportRect` and its siblings follows the zoom, as do the
built-in menus and popovers. `editor.on("zoom", …)` fires with the new and previous factor
and the request; `"viewport"` fires with it when the factor changes. Page-unit values —
`layout`, `charMap`, `getNodeRect` — are the same at every zoom. `getPageScreenPosition(page)`
gives a page's corner on screen; a page-unit offset from it is `offset × editor.zoom` pixels.

The caret, resize handles, collaborators' cursors and drag feedback keep their size on
screen. An overlay handler that wants the same sizes itself with `screenPixels(n)`, which is
valid only while an overlay paints.

## Virtual scrolling and overscan

`TileManager` paints the pages in view plus `overscan` pages above and below. Increase it if
users see blank pages during fast scrolling:

```tsx
<Scrivr editor={editor} overscan={2} />
```

Default is `1`. Each step paints one more tile above and below the view, two canvases each
(smoother fast scrolling, more memory).

## Observing the current page

`editor.cursorPage` returns the 1-based page number of the current cursor position:

```ts
const page = editor.cursorPage; // e.g. 3
```

Subscribe to updates to drive a reactive page indicator:

```tsx
function PageIndicator({ editor }: { editor: Editor }) {
  const page = useEditorState({
    editor,
    selector: ({ editor }) => editor?.cursorPage ?? 1,
  });

  return <span>Page {page}</span>;
}
```

## Programmatic scrolling

`scrollCursorIntoView()` scrolls the viewport so the current cursor is visible. It is called
automatically after every cursor move — you only need it when moving the cursor programmatically:

```ts
editor.moveCursorTo(targetPos);
editor.scrollCursorIntoView();
```

To scroll a page's top to the top of the view — at any zoom, since the page's corner is where
it is drawn now:

```ts
const scroller = document.querySelector(".my-editor-scroller"); // the editor's scroll container
const corner = editor.getPageScreenPosition(pageNumber);
const view = editor.getScrollContainerRect();
if (scroller && corner && view) {
  scroller.scrollBy({ top: corner.screenTop - view.top, behavior: "smooth" });
}
```

## Converting positions to screen coordinates

`getViewportRect(from, to)` maps a doc-position range to a viewport-relative `DOMRect`.
Use it to position floating UI elements — menus, tooltips, link popovers — relative to text:

```ts
const snap = editor.getSelectionSnapshot();
const rect = editor.getViewportRect(snap.from, snap.to);

if (rect) {
  tooltipEl.style.top  = `${rect.bottom + 8}px`;
  tooltipEl.style.left = `${rect.left}px`;
}
```

Returns `null` when the positions are not in the character map or no rendering adapter is mounted.

For a node — an image, a paragraph, a table — use `getNodeViewportRect(docPos)` instead. It
returns a rect covering the node's visual bounds (for a node split across pages, its first
fragment; `getNodeViewportRects` returns all of them):

```ts
const rect = editor.getNodeViewportRect(imageDocPos);
if (rect) {
  toolbar.style.top  = `${rect.bottom + 8}px`;
  toolbar.style.left = `${rect.left}px`;
}
```

## Manual layout control

These methods are rarely needed — the layout engine runs automatically after every transaction.

```ts
// Force a synchronous layout pass if stale
editor.ensureLayout();

// Lay out and index a specific page (useful for off-screen coordinate lookups)
editor.ensurePagePopulated(5);

// Trigger a repaint without a doc/selection change (e.g. after awareness data updates)
editor.redraw();
```
